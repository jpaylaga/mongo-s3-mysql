# Limitations

## What the pipeline cannot do

- No change data capture: deletes never propagate; in-place updates arrive only when their window is re-exported; `reconcile` cannot detect an update lost between export and retirement ([reconcile](reconcile.md#what-reconcile-cannot-see)).
- Deltas follow the window field. Creation times and ObjectIds catch inserts only; back-dated writes older than `since` are missed; rest documents need `--include-rest`.
- Each chunk is checked only by its own before and after count. A write during a `full-collection` walk flags the chunk, so a busy small collection is flagged in every delta: export it in a quiet window, load it with `--allow-mismatch` and re-export it fully later, or window it.
- Window values at or after the cutoff (future dates, fast clocks), before an explicit `start`, or of the wrong type (a string where a date is expected, a UUID `_id` under `objectid-window`) are in no window. They are counted in the batch manifest's `out_of_range` (`after_cutoff`, `before_start`, `untyped`) and exported only by a planned rest chunk (`rest: auto` skips it above 1,000,000 documents; deltas skip it without `--include-rest`). Check the counts before the final batch. A windowed collection in which no document has a window-typed value refuses to plan without the rest chunk, and a grid of more than 100,000 windows (a sentinel minimum such as 0001-01-01) needs `collections[].start`.
- A failed attempt restarts the whole chunk; use `hour` windows for busy collections. A `timestamp-window` rest chunk may scan far ([DocumentDB notes](documentdb.md#rest-scans)).
- `_id` values outside the 8 keyset brackets (null, MinKey, MaxKey, NaN, code, DBPointer) are never exported: the chunk that counts them (a `full-collection` chunk, or a windowed collection's rest chunk) fails its count check and is flagged, so the loss is visible. Keys cast only to `objectId`, `string` or `bigint`; any other `_id` rejects the line at load, and `infer` writes no mapping when no sampled `_id` fits a key cast.
- Datetimes are wall-clock strings; `TIMESTAMP` columns depend on `mysql.sessionTimeZone`. A bare relaxed integer beyond 2^53 was already rounded by `JSON.parse`, so such a line is rejected for the key and the integer and decimal casts rather than merged with another document; canonical `$numberLong` carries the digits.
- One table per collection, one level of child tables, child rows are not reconciled; across batches the last writer wins.
- The key ledger costs about 110 bytes per ObjectId document; without it only `reconcile --deep` proves coverage.
- MySQL 8.0.19+ (row-alias upserts); MongoDB 4.4+ or DocumentDB 5.0+ (the driver refuses older servers).
- Resuming an older batch behind a loaded newer one needs the newer one in the same run: `load --reload --batch-id <older>,<newer>` or `--allow-older`. The guard is per table and per chunk: every newer chunk that wrote rows to that table (loaded, or interrupted with `lines_done > 0`) must be a candidate in the run, and it is then replayed from line 0 after the older batch whatever its `lines_done` says. A chunk skipped as already loaded does not count, since its rows would not be rewritten.
- A JavaScript object moves integer-like keys (`"0"`, `"42"`) to the front, so a document whose fields include such keys is archived with those keys first; the canonical line does not keep the source field order. An embedded-document `_id` with such a key at any depth (a nested subdocument or an array element included) cannot be paged exactly and fails its chunk with a clear `parse` error.
- A BSON date outside the JavaScript range (beyond +/-8.64e15 ms) cannot be represented by the driver; the chunk fails instead of archiving `NaN`.

## Implementation notes

The decisions a reader of the code or the records may wonder about, in one place.

### Locks

- `acquireLock` creates the lock file with its body in one step (temp file plus hard link) and takes a stale lock over through a private rename that is undone when the body changed meanwhile. The holder touches the lock every 30 seconds, and no takeover (short of `--force-unlock`) happens while the heartbeat is fresh: a pid that is gone or replaced from here is taken over once untouched for 90 seconds, because a holder in another PID namespace on the same hostname is invisible to `kill(pid, 0)` and shows another identity in `/proc` yet still touches its lock; a lock naming this process's own pid that it does not hold only once untouched for five minutes, because a sibling container that is also pid 1 (shared hostname, shared `stateDir`) looks exactly like a restart from inside a PID namespace. Until then a lock is refused as live. A lock from another host is never judged, it needs `--force-unlock`. Between a mistaken rename and its put-back the lock name is briefly free, so a third contender arriving in that instant can take a lock the real holder still uses; it takes three contenders on one state directory at once.

### Export

- The rest-chunk decision (`rest: auto` with at most 1,000,000 documents, `rest: export` or `skip`, `--include-rest`, never in deltas without `--include-rest`) is taken when the batch is resolved, not when chunks are planned, because it is frozen into the batch manifest's `plan`. On resume, `--include-rest` and per-collection `rest` settings are ignored in favour of the frozen plan, silently; `--since last` is a no-op with an info line, and an explicit `--since` or `--cutoff` must equal the frozen value.
- A new batch's `--cutoff` may not be in the future (its windows would run now and `--since last` would start after the writes they missed); one inside `safetyLagMinutes` only warns.
- A gunzip-test line-count mismatch before upload is reported with code `sha256` (the chunk is retried); a stored-size mismatch after upload with code `s3`.
- A chunk whose count is refused under its index hint is recounted without a hint, before and after the read. A chunk that counts zero reads nothing: the brackets would otherwise be walked anyway, and a rest chunk's empty filter under `_id_` would scan the whole collection; a write that lands meanwhile still shows in the after count.
- A `manifest-only` chunk whose collection filled up in the meantime writes nothing (a flagged record would outlive the resume and block every load of that collection) and ends `mismatch`; the batch is `partial` and the next run with the same `--batch-id` plans the collection with a strategy.
- Each chunk attempt re-reads its manifest first and skips the chunk when another exporter committed it meanwhile (two runners on one batch from different state directories); it never overwrites a `counts_match: true` manifest.
- `perCollection.done` in the export result counts chunks committed in earlier runs plus this run; `failed` counts failed and interrupted outcomes.
- The batch manifest's `completed_at` is set at the end of every invocation, including an interrupted one; `status` tells whether the batch is complete.
- The S3 store used by the CLI never aborts on the run signal: after SIGINT the final batch manifest must still be written. Uploads are abandoned through their own per-call signal; the HTTP request already in flight is not cancelled by the SDK, so S3 may finish storing it. After a non-signal error the attempt waits for the upload to settle instead, so a late PUT can never land under the next attempt's manifest.
- A signal that arrives after the last chunk committed leaves the batch `complete` (the exit code is still 130 or 143), so `--since last` can build on it.
- Counts from the driver are coerced to numbers: the client runs with `promoteValues: false` so documents keep their BSON types, and `countDocuments` then returns `Int32` or `Long` objects.
- `--since last` on a batch without a frozen plan (another exporter's) covers a collection only when a chunk manifest of that batch exists for it, or a foreign delta names it in `collection_start_utc`; the earlier rule ("a plan-less batch covers everything") gave a collection added to the config later a delta start that skipped its whole history.
- The pre-check that skips a chunk another exporter committed meanwhile swallows only an unreadable manifest (a `record` error); an S3 failure retries the chunk or, when fatal, stops the run before anything is read.
- Every S3 body the store hands out or reads carries an idle watchdog of 120 seconds (the SDK clears its own socket timer once the response headers arrive, so a body that stalled after the headers would otherwise hang until TCP keepalive gives the path up); the `TimeoutError` it raises retries. Record reads (`getText`) are capped at 64 MiB, sidecar reads at 1 KiB: a larger object at a record key is a `record` error, never a string of its size.

### Verify

- The batch completeness check counts the chunk manifests of every discovered collection, whatever the config lists (only the listed collections' parts are read); it is skipped with an info line only under `-C`, since a narrowed selection counted against `completed_chunks` would report false missing batches. A chunk manifest or batch manifest that does not parse is one damaged record (exit 3, a failing parse-check with `record: ...` and the zod detail naming the field), not the end of the run; its `counts.json` is left as the exporter wrote it, and the failing parse-check is written only after the prompt is accepted. A `--batch-id` with no batch manifest and no chunk manifest under the prefix is a config error, and so is a `-C` name that is not under the prefix. A batch manifest that does not parse is reported in its own `invalidBatches` field with its own hint (versioning, since export reads that manifest first and cannot resume the batch), never as a batch with missing chunk manifests. By default only chunks without a passing parse-check for their current manifest body are read; `--all` re-reads every chunk.
- Chunk attempts are a fixed 3 (there is no `verify.chunkAttempts` key). `VerifyResult.missing` holds batch ids; the shortfall is a warning. Flagged chunks (`counts_match: false`) do not count toward `completed_chunks`.
- A dry run prints totals (objects, bytes, chunks, already verified, batches, collections) and exits 0 without the batch check. The verify lock is taken for `--dry-run` and `--no-write` runs too.
- The record checks also include: `run_id` and `collection` must equal the key's; `parts[].lines` is checked per part when present; `file` must equal the first part; non-manifest-only chunks must have `format: canonical_extended_jsonl_gzip`; a content part with a null `checksum_s3_uri` is an error. A part addressed outside the bucket or the chunk's raw prefix is reported once and not read.
- When decoding ends early (a gunzip failure, invalid UTF-8, or a line over 256 MiB), the object is read a second time for its size and sha256 alone, so `bytes_ok` and `sha256_ok` describe the object and the line-count checks are not reported; `gzip_test` is null when the text, not the compression, was the problem. The second read only happens for damaged parts.
- Damaged chunks come back as `mismatch` with the first three errors in the event; unreadable ones as `failed` with the redacted error in `operational`; interrupted ones with `operational: interrupted`.

### Infer and mapping

- Decimal precision is `min(65, 2 x intDigits + 4 + scale)` with the scale clamped to 30: the golden mapping needs `DECIMAL(14,2)` for a column with 4 integer digits seen and `DECIMAL(10,2)` for one with 2, so the headroom is twice the integer digits, not a fixed four.
- Inside an array of objects, element presence is measured against the most frequent element field's count, so a lone element field is always 100% present.
- Identifier fallback beyond the derivation table: a field whose snake form is empty and whose raw name is not a legal identifier either (`---`) becomes `f_<6 hex of sha1(field)>`; `__` stays `__`.
- `infer --table` with more than one selected collection is refused; its value is used verbatim (`--table ArchivedOrders` creates `ArchivedOrders`), while the default table is `snake(collection)`. Without `--batch-id`, each collection is sampled from the newest finished full batch (not `running` or `interrupted`) that holds documents of it, falling back to the newest delta only when no full batch holds it, since a delta holds only its last windows; a collection that gets no mapping, or whose parts or manifests cannot be read (a missing part, a misaddressed one, a damaged record, a line too deep to analyse), is reported and the run exits 2 after the others. Element stats of arrays of objects are fed one element at a time and stop 32 levels deep, so a document with 150,000 subdocuments or a line nested thousands of levels deep (a foreign or tampered archive) costs no extra memory and cannot overflow the stack. A child element's own `_id` (the Mongoose default) is mapped as a child column.
- The mapping sha256 hashes the parsed mapping (defaults applied) minus `inferred`, `$schema`, every `note` and every `sqlType` (DDL hints change nothing the load does), with a spelled-out `fsp: 0`, `timezone: "UTC"` or `round: "reject"` dropped like an absent one, so spelling out a default, editing a comment or re-running `infer --force` with a wider VARCHAR does not force a reload. Release note: this changed the sha once; the first load after upgrading reports every chunk as `loaded with another mapping; pass --reload` and `--reload` re-applies them. `Invalid mapping <path>:` errors are fatal config errors; invalid JSON reports the parser's message, since mapping files hold no secrets.
- `infer` sizes a string key from its own ladder (32 to 760 characters, the key ledger's width and inside InnoDB's utf8mb4 index limit) and never TEXT; a sampled `_id` over 760 characters gets a review line. When no sampled `_id` fits any key cast (UUID binaries, doubles), no mapping is written and the collection counts as failed (exit 2). `infer` always writes under `mappingsDir` (or `--out`) and warns when `collections[].mapping` points elsewhere, so it never overwrites a curated file.
- `mappingToDdl` without `sqlType`: `decimal` becomes `DECIMAL(65,30)` (the widest value the clamp can produce), `datetime` becomes `DATETIME(<fsp or 0>)`, `string` becomes `VARCHAR(255)`. A string key gets `COLLATE utf8mb4_0900_bin` on `VARCHAR` only (a `COLLATE` on `VARBINARY` is an error); a `CHAR` or `BINARY` key `sqlType` is refused before any DDL runs, since the shape check would refuse the table it created. A child with `indexColumn: null` gets a non-unique `KEY ix_<child>_parent (parentColumn)`, because several elements then share one parent key; with an index column the key is unique. `infer` turns the widest `VARCHAR` columns into `TEXT` until the estimated row (`4n + 2` bytes per utf8mb4 `VARCHAR(n)`) stays under MySQL's 65,535-byte limit.
- `castValue` enforces what MySQL would refuse under `STRICT_ALL_TABLES` so one line can never fail its batch: lengths (code points for CHAR and VARCHAR, bytes for the text, VARBINARY and BLOB types), the column's character set from its collation prefix (utf8mb3 and ucs2 stop at U+FFFF, latin1 is cp1252, ascii is 7-bit), ENUM and SET membership (case-insensitive unless the collation is binary, `_bin` or `_cs`), the integer ranges (a double is rounded half away from zero first, as MySQL does), UNSIGNED on DECIMAL, FLOAT and DOUBLE, FLOAT's range (FLT_MAX exactly), and the integer digits of DECIMAL(p,s) and of the FLOAT(M,D) and DOUBLE(M,D) of older schemas, counted after rounding at the scale, for every numeric cast (a `decimal` into an integer column is rounded half away from zero at scale 0, as MySQL does, and must then be in range). Every value is also checked against the live column's type family: any cast into a text or binary column is bound by that column's length and character set (an ObjectId into `CHAR(12)`, a number into `VARCHAR(5)`), a string or JSON text into a numeric column must be a whole decimal literal that fits (MySQL skips trailing whitespace, and leading whitespace before DECIMAL, FLOAT and DOUBLE, but only leading spaces and tabs before an integer column: `"\n12"` is error 1366 there), a string into a JSON column must parse as JSON, a `datetime` or `objectId` into a JSON column never fits, and a number (`int`, `double`, `bool`) into a JSON column is sent as its text, since mysql2 writes a number unquoted and MySQL refuses that (error 3140) while the quoted text is the same JSON value. A number into ENUM or SET is read as MySQL reads it (1-based member index, bit mask over the members; a quoted `bigint` or `decimal` text matches a member by text first) and anything else there, a date or ObjectId text included, is a cast error (MySQL's 1265). Verified against MySQL 8.0.42 under the loader's `sql_mode` for each of these cases. A numeric `$date` must be an integer, a string `$date` must carry an offset (otherwise the loader host's zone would decide the instant), and a `$numberDouble` payload must be a decimal literal (`Number()` would read `""` and whitespace as 0 and accept hex). What it cannot foresee (a foreign key, a CHECK constraint, a trigger) still fails the batch and, after the attempts, the chunk; the error is in `_msm_load_chunks.error`.
- `castValue`: `json` into a JSON column has no byte budget of its own (`information_schema` gives JSON columns no octet length); into a text or varchar column it is bound by that column's length like a string, and so is the extra column. A row larger than the batch byte budget but within 90% of `max_allowed_packet` forms a batch of its own; one larger than the packet is rejected as `row larger than max_allowed_packet`. A missing, null or uncastable value for a NOT NULL column without a mapping default rejects the line whatever `onCastError` says. A `$numberDecimal` exponent beyond +/-6200 or more than 65 integer digits is a cast error, never an allocation. `decimal` drops non-significant trailing fraction zeros (`10.00` to `10`), which MySQL stores identically, so such zeros never count as digits beyond the scale. `datetime` checks the `TIMESTAMP` range on the UTC instant (`1970-01-02 00:00:00` to `2038-01-18 23:59:59`, leaving room for any session time zone) and the year 1000..9999 on the formatted wall clock.
- `checkTableShape` reports the "key column over 760 characters" problem only while `load.keyLedger` is on, and `mappingToDdl` (given `keyLedger`) refuses a string `key.sqlType` over that width before any `CREATE TABLE`, so `--create-tables` cannot create a table the recheck then refuses; `reconcile --deep` inserts keys into a VARCHAR(760) temporary table and ends the check with a config error naming the line when a longer key turns up, since a truncated key would merge with its neighbours into false drifts. The width and collation live in one place (`mysql/keyLedgerKey.ts`) for the ledger DDL, the shape check, infer's key ladder and the deep check. The shape check also refuses pairs no value could ever fit (an `objectId` key or column on a numeric column or one shorter than 24, a `json` cast on a numeric column), a `chunkColumn` that is not `BIGINT`, `BIGINT UNSIGNED` or text, and an `extraColumn` that is not JSON or text or is `NOT NULL`; a `TIMESTAMP` column warns whenever the cast zone's current UTC offset differs from `mysql.sessionTimeZone`, naming both. A string key (and a child's `parentColumn` under a string key) needs a NO PAD binary collation (`utf8mb4_0900_bin`, or a VARBINARY column, which information_schema reports without a collation and `readTableInfo` names `binary`): `utf8mb4_bin`, `ascii_bin` and the other pre-8.0 `_bin` collations pad trailing spaces, the `_0900_as_cs` collations compare UCA weights (canonically equivalent strings share a row), and CHAR strips trailing spaces. A prefix UNIQUE key (`UNIQUE (k(10))`) on the key column is refused: it collides on the prefix in MySQL but not in the loader. The `fsp` rule applies only to DATETIME, TIMESTAMP and TIME columns; a datetime into a string column is checked for the literal's length instead. A `runIdColumn` must be a string column at least as wide as the run id, and a child's `parentColumn` must be indexed (a warning at `load.concurrency` 1, a problem above it: the per-batch DELETE would scan and deadlock).
- `readTableInfo` reports `dataType` as `<DATA_TYPE lowercased>[ unsigned]` so integer ranges can be chosen, treats generated columns as having a default (they are never written), and lists the leading column of every index as `indexedColumns` for the chunk-column warning.
- `createMysql` opens one probe connection first: `SELECT VERSION()`, the version check, the two session statements (`SET NAMES utf8mb4` and the `SET SESSION ...` sentence) and `@@max_allowed_packet`, so a server that refuses any of them fails with its own message before a pool exists. The pool then runs the same statements from its `connection` event, ahead of any user query; a failing statement there destroys that connection. `connect()` opens a dedicated connection with the same statements. Every connection sets TCP keepalive at 30 s; the lock ping, the lock check and the holder's own GET_LOCK, session and RELEASE_LOCK statements carry a 30 s query timeout (a stalled socket there is a lost lock, and a failure after GET_LOCK destroys the connection so the lock is never leaked), and every statement of a batch a 10 minute one, START TRANSACTION, COMMIT and ROLLBACK included. A mysql2 query that times out is rejected but stays the connection's current command, so the connection is destroyed right after any of these timeouts (`writeBatch` skips the ROLLBACK, the server rolls back with the session; the lock holder skips RELEASE_LOCK and `end()`): nothing waits for the OS to give the half-open socket up.

### Inventory

- `suggestStrategy` computes the `hour` rule for `objectid-window` as the estimated count divided by the day span between the ObjectId time bounds (a span under one day counts as one day); without bounds the rate is unknown and `day` stands. `timestamp-window` suggestions always use `day`, since the newest-N sample cannot estimate a rate.
- The default sample size is 1,000 when `--sample` is omitted.
- Exit codes: 0 for type skips (views, time series, `system.*`) and names that do not exist, 2 when a collection was skipped because of a non-fatal error; fatal errors and aborts propagate.
- `--write-config` validates the config (position-only JSON errors, the secrets guard) and refuses a non-empty list without `--force` before connecting, omits `window` for `full-collection` entries, keeps an existing same-name entry's `start`, `rest` and `mapping`, validates the result before writing, and leaves the file unchanged when nothing was inventoried. `init` writes the example with an empty list, so the documented next step needs no `--force`.

### Load

- The batcher takes a `rejectTuple` formatter so a row tuple larger than 90% of `max_allowed_packet` can be turned into a reject (`row larger than max_allowed_packet`, or `child row larger than max_allowed_packet` when one child tuple is); a row that only exceeds `load.batchMaxBytesMb` forms a batch of its own. The child tuples are formatted once in `loadChunk` and count toward the batch budget, so a batch of array-heavy documents stays near the budget. The reject's text is the first 16,384 UTF-8 bytes of the SQL tuple, since the batcher never sees the line.
- `selectChunks` returns skips as `{ resolved, reason, severity }` so the exit code (2, warning, or quiet resume) does not depend on parsing the reason text; the reasons are the fixed strings docs/operations.md quotes.
- The order guard is scoped per target table and per chunk using that table's ledger rows (see the first section); a newer chunk that must replay is forced to `reload`, which `loadChunk` honours for loading rows too. The obligation is persisted before the older batch writes: under the table locks, every forced chunk's ledger row is set to `status loading` with the sentinel `manifest_sha256` `replay-pending-000...`, so a run interrupted between the two batches is followed by a plain `load` that still replays the newer chunk from line 0. The plan is taken twice: once for the prompt, once under the GET_LOCKs on the ledger as it is then; a difference (another loader finished a batch on that table meanwhile) stops the run. A load with an empty collection list discovers the archive's collections, like verify and reconcile. `--load-run-id` is 1 to 64 printable ASCII characters, no spaces. A candidate's `reload` (from `--reload` or a forced replay) is cleared once its reset ran, so a later attempt of the same chunk resumes from the committed `lines_done` instead of replaying what the first attempt committed.
- The GET_LOCK holder connection (`acquireTableLock`) gets `wait_timeout` raised to a year and a `SELECT 1` every 60 s with a 30 s timeout; a failure or timeout on it destroys the connection and ends the run with `lock on <table> lost`, as does a failed `IS_USED_LOCK` check at a chunk start (which destroys it too, so the lock release at the end sends nothing on a dead socket).
- The ledger DDL runs only for ledger tables that do not exist yet (`CREATE` is checked before `IF NOT EXISTS`), so a loader with DML grants works once the tables exist.
- `omitPaths` removes array indices against the original positions (higher index first), so two index sources on one array consume the right elements.
- `--create-tables` filters the `missing table <name>:` problems out of the shape report, runs their `CREATE TABLE` statements after the confirmation, then reads and checks the created tables again. The `_msm_load_keys` statement is skipped when `load.keyLedger` is false.
- The export command sets `process.exitCode` instead of calling `process.exit`, so stdout flushes before the process ends. An interrupt before the chunk phase (during planning, the prompt, the DDL, the table locks or the second ledger read) returns 130 or 143 like one during it; no rows were loaded then, though the ledger tables (and `--create-tables` DDL) may already exist. Only a prompt declined or interrupted at the TTY exits 1. Inventory returns the collections read so far with the signal's code too.
- Stdout and stderr carry an `error` listener, so a closed pipe (`2>&1 | head`) never kills a run on EPIPE; text-mode lines, the fatal message and the `next:` hint escape control characters (archive ids and record values reach all three), JSON lines and the `--json` document are redacted field by field before serialization and get `\\u00XX` escapes for DEL and the C1 controls, which JSON.stringify leaves raw. The `next:` hints are full command lines that repeat the `-c` and `-C` flags of the run.
- Chunk discovery accepts a manifest only at its canonical key, and a part whose `s3_uri` is outside its chunk's raw prefix gets no key: verify names it, and load, infer and reconcile refuse it as a record error without asking S3 for it.
- The export's local cache (`completed.jsonl`) only records committed chunks (`counts_match: true`) with their manifest key and bucket, and only stands in for a manifest the S3 listing returns under its canonical key (a copy nested deeper under the prefix is not a commit): a cleaned prefix or another bucket plans everything again. The rest chunk's after-cutoff term leaves out the live writes in `[startedAt, max(startedAt, attemptStart) + 1 day)` (the frozen `[cutoff, startedAt)` stays in; a resume two days later leaves out three days), so a rest chunk run a day or more after the batch began can still commit on a live collection; the manifest's `filter.query` records the term that was used. For `objectid-window` the rest filter also counts `_id` values outside every bracket (null, MinKey, MaxKey, NaN, code, DBPointer), so they flag the chunk instead of vanishing.

### Reconcile

- `--deep` reads the selected chunks in ledger (load) order and reuses the load's part download (bytes and sha256 checked); an abort is honoured between parts, not mid-download, and returns the drifts found so far with exit 130 or 143. `--deep` takes the `reconcile` lock in `stateDir` because its downloads share one directory, and wipes that directory first like export and load do, so a crashed run's parts do not stay behind; a plain reconcile takes no lock. A run that checked no table (no selected collection has a mapping) is a config error, not exit 0, and so is a `-C` name without a mapping or without any chunk manifest or ledger row.
- Two collections that load one table are matched to their own ledger rows (`_msm_load_chunks.collection`) for the record checks, and the table-side proofs run once per table over the union of their rows and manifests; they must share the key column. A `--batch-id` that no batch manifest, chunk manifest or ledger row knows is a config error.
- A ledger row whose manifest object no longer exists is reported as `manifest_changed` with a detail saying the object is gone.
- `tableCheck` also reports `chunk_count` for rows tagged with a selected chunk's id whose key that chunk never wrote, and returns `expected` and `actual` (null without the key ledger) so `deep_distinct` needs no second query. A selected chunk that wrote rows but has no key rows (loaded while `load.keyLedger` was off) or fewer key rows than `rows_inserted` (switched off half-way), and every such chunk when `_msm_load_keys` does not exist at all, is `unproven`: left out of both key-ledger proofs, named in a warning, and `deep_distinct` is skipped for that table.
- `--deep` skips the lines `_msm_load_rejects` records for a chunk and the lines past an unfinished chunk's `lines_done`, so ordinary rejects and `load_incomplete` rows never show up as `missing_rows`.
